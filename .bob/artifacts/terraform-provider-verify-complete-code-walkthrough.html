1. Architecture Overview

The codebase has three distinct layers. Each layer has one job and does not reach into the others' responsibilities.

Pure logicinternal/crypto/Go functions that generate certs and JWTs. No Terraform code. Independently testable.

2. main.go — Entry Point

main.goGo
func main() {
    providerserver.Serve(
        context.Background(),
        provider.New,   // ← factory: returns a new VerifyProvider
        providerserver.ServeOpts{
            Address: "registry.terraform.io/christian-verderame/verify",
        },
    )
}

When Terraform runs terraform apply it looks up the provider binary on disk (via the dev_override in ~/.terraformrc) and launches it as a child process. The binary starts a gRPC server inside providerserver.Serve(). Terraform then connects to that server and sends RPCs like "plan this resource" or "create this resource".

Address matters: The address christian-verderame/verify must exactly match the source field in required_providers in every .tf file that uses this provider.

provider.New is a factory — a function that returns a new provider instance. The framework calls it once per Terraform operation.

3. internal/provider/provider.go — The Registry

internal/provider/provider.goGo

This is the directory listing of everything the provider offers. It implements the provider.Provider interface — five methods Terraform calls at startup:

MethodWhat it returns / does
Metadata()Sets TypeName = "verify" — this prefix is added to all resource names, making verify_jwt, verify_certificate, etc.
Schema()Declares provider-level config (currently empty — no global tenant_url yet)
Configure()Runs after Terraform reads provider config. Currently empty — would build a shared HTTP client here in future and pass it to all resources via resp.ResourceData
Resources()Returns []func() resource.Resource — a slice of factory functions, one per resource type
DataSources()Returns []func() datasource.DataSource — same pattern for data sources
func (p *VerifyProvider) Resources(...) []func() resource.Resource {
    return []func() resource.Resource{
        resources.NewCertificateResource,   // → "verify_certificate"
        resources.NewJWTResource,           // → "verify_jwt"
        resources.NewTokenExchangeResource, // → "verify_token_exchange"
    }
}
func (p *VerifyProvider) DataSources(...) []func() datasource.DataSource {
    return []func() datasource.DataSource{
        datasources.NewTokenIntrospectionDataSource, // → "data.verify_token_introspection"
    }
}
Why factory functions? Terraform may create many instances of a resource type in one run. Using a factory (func() resource.Resource) means each instance gets a fresh zero-value struct — no shared state between instances.

4. internal/crypto/certificate.go — RSA Key + Cert Generation

internal/crypto/certificate.goGo — pure logic, no Terraform

A single exported function: GenerateSelfSignedCertificate(request). Takes inputs, returns (CertificatePEM, PrivateKeyPEM) as strings.

Step by step

// 1. Validate inputs (common_name, org, country, validity, key_size)
if request.KeySize != 2048 && request.KeySize != 3072 && request.KeySize != 4096 { error }

// 2. Generate a random RSA private key — DIFFERENT EVERY TIME
privateKey, _ := rsa.GenerateKey(rand.Reader, request.KeySize)

// 3. Generate a random 128-bit serial number for the certificate
serialNumber, _ := rand.Int(rand.Reader, new(big.Int).Lsh(big.NewInt(1), 128))

// 4. Build the certificate template
template := x509.Certificate{
    SerialNumber: serialNumber,
    Subject:      pkix.Name{ CommonName: "DemoTokenSigner", ... },
    NotBefore:    now - 5min,   // small backdate to avoid clock-skew rejections
    NotAfter:     now + 365days,
    KeyUsage:     DigitalSignature | KeyEncipherment,
    ExtKeyUsage:  ClientAuth,   // this cert is used to authenticate a client
    IsCA:         false,
}

// 5. Self-sign: the cert is signed by itself (same template as parent and child)
certDER, _ := x509.CreateCertificate(rand.Reader, &template, &template, &privateKey.PublicKey, privateKey)

// 6. Encode both to PEM strings and return
return &CertificateResult{ CertificatePEM: "-----BEGIN CERTIFICATE-----...", PrivateKeyPEM: "-----BEGIN RSA PRIVATE KEY-----..." }
Generates a new key pair every call. rsa.GenerateKey(rand.Reader, …) uses the OS cryptographic random number generator — it is mathematically impossible to produce the same key twice. This is why the cert lives in its own separate Terraform root that is never destroyed.

5. internal/resources/certificate_resource.go — verify_certificate

internal/resources/certificate_resource.goGo — Terraform resource

The Terraform wrapper around GenerateSelfSignedCertificate(). Implements the resource.Resource interface.

The model struct

type CertificateResourceModel struct {
    CommonName   types.String `tfsdk:"common_name"`    // Required input
    Organization types.String `tfsdk:"organization"`   // Required input
    Country      types.String `tfsdk:"country"`         // Required input
    ValidityDays types.Int64  `tfsdk:"validity_days"`   // Required input
    KeySize      types.Int64  `tfsdk:"key_size"`         // Required input
    CertificatePEM types.String `tfsdk:"certificate_pem"` // Computed output
    PrivateKeyPEM  types.String `tfsdk:"private_key_pem"` // Computed output (sensitive)
}

The tfsdk:"…" struct tag is how the framework maps an HCL attribute name to a Go field. types.String (not plain string) is used because Terraform values can be null, unknown, or a real value — the framework's type wraps that.

Schema — what Terraform knows about the resource

AttributeRequired / ComputedPlan modifier
common_nameRequired (user provides)RequiresReplace()
organizationRequiredRequiresReplace()
countryRequiredRequiresReplace()
validity_daysRequiredRequiresReplace()
key_sizeRequiredRequiresReplace()
certificate_pemComputed (provider fills in)none
private_key_pemComputed + Sensitivenone
RequiresReplace(): Tells Terraform "if the user changes this field, destroy the old resource and create a new one." Because a certificate is cryptographic material — you can't edit it in place — every input has this modifier.

Create — the only method that does real work

func (r *CertificateResource) Create(ctx, req, resp) {
    var plan CertificateResourceModel
    req.Plan.Get(ctx, &plan)             // 1. read HCL config into the struct

    result, _ := crypto.GenerateSelfSignedCertificate(...)  // 2. generate cert

    plan.CertificatePEM = types.StringValue(result.CertificatePEM)  // 3. set outputs
    plan.PrivateKeyPEM  = types.StringValue(result.PrivateKeyPEM)

    resp.State.Set(ctx, &plan)           // 4. save everything to Terraform state
}

Read, Update, Delete are all empty — there is nothing to read back from an external system (the cert was generated locally), nothing to update (RequiresReplace handles changes), and nothing to delete (it's just state).

6. internal/crypto/jwt.go — JWT Signing

internal/crypto/jwt.goGo — pure logic, no Terraform

A single exported function: GenerateSignedJWT(request). Uses the github.com/golang-jwt/jwt/v5 library.

// 1. Parse the RSA private key PEM string into a Go *rsa.PrivateKey
privateKey, _ := jwt.ParseRSAPrivateKeyFromPEM([]byte(request.PrivateKeyPEM))

// 2. Build the standard JWT claims
claims := jwt.MapClaims{
    "iss": "https://demo.ibm.com",       // who issued the token
    "sub": "bretton",                    // who the token is about
    "iat": now.Unix(),                   // issued at (Unix timestamp)
    "exp": now.Add(15min).Unix(),        // expires at
    "jti": "some-uuid",                  // unique ID — prevents replay attacks
}

// 3. Create token with RS256 algorithm
token := jwt.NewWithClaims(jwt.SigningMethodRS256, claims)
token.Header["kid"] = "demotokensigner"  // key ID — IBM Verify uses this to look up the cert

// 4. Sign with the private key → produces the three-part JWT string
signedToken, _ := token.SignedString(privateKey)
// Result: "eyJhbGci....eyJpc3MiO....FLPzuUKRA9..."
//          ↑ header    ↑ claims      ↑ signature

Why kid matters

IBM Verify stores your uploaded certificate under a label (e.g. demotokensigner). When it receives a JWT it reads the kid header, looks up the certificate by that label, and uses the certificate's public key to verify the signature. If kid doesn't match any stored label → rejected.

7. internal/resources/jwt_resource.go — verify_jwt

internal/resources/jwt_resource.goGo — Terraform resource

The Terraform wrapper around GenerateSignedJWT(). Follows the exact same pattern as certificate_resource.go.

AttributeTypeDescription
issuerRequiredGoes into iss claim
subjectRequiredGoes into sub claim — the username IBM Verify resolves
key_idRequiredGoes into kid JWT header — must match the cert label in IBM Verify
jwt_idRequiredGoes into jti claim — a UUID for uniqueness
private_key_pemRequired + SensitiveThe RSA private key used to sign
expires_in_secondsRequiredHow long the JWT is valid (900 = 15 min)
tokenComputed + SensitiveThe signed JWT string
issued_atComputedUnix timestamp of signing time
expires_atComputedUnix timestamp of expiry
Known limitation: All inputs have RequiresReplace(). Since key.pem and other inputs don't change between runs, Terraform keeps the old (expired) JWT in state. You must terraform destroy -target=verify_jwt.custom to force a fresh one. This is why every apply should be preceded by destroying the JWT and token exchange resources.

8. internal/client/token_exchange.go — HTTP Token Exchange

internal/client/token_exchange.goGo — HTTP client, no Terraform

A single exported function: ExchangeToken(ctx, request). Sends an OAuth 2.0 Token Exchange (RFC 8693) request to IBM Verify.

// POST https://<tenant>/oauth2/token
// Content-Type: application/x-www-form-urlencoded

form := url.Values{}
form.Set("grant_type",          "urn:ietf:params:oauth:grant-type:token-exchange")
form.Set("client_id",           "9ada0c66-...")
form.Set("client_secret",       "TvFt1rBA9...")
form.Set("subject_token",       "<the signed JWT>")
form.Set("subject_token_type",  "urn:demo:token-type:user-jwt")

Response handling

// Success (HTTP 200):
{ "access_token": "tNAJt3...", "expires_in": 3600, "grant_id": "67c35bc8...",
  "issued_token_type": "urn:ietf:params:oauth:token-type:access_token",
  "scope": "", "token_type": "bearer" }

// Failure (HTTP 4xx):
{ "error": "invalid_client", "error_description": "CSIAQ0155E..." }
// → returned as a Go error with the HTTP status code and both fields

Error guard at line 134

if tokenResponse.AccessToken == "" {
    return nil, errors.New("IBM Verify response did not contain an access_token")
}

Even if the HTTP status is 200, if access_token is missing the function returns an error — defensive programming against unexpected IBM Verify response formats.

10. internal/client/introspection.go — HTTP Introspection

internal/client/introspection.goGo — HTTP client, no Terraform

A single exported function: IntrospectToken(ctx, request). Sends an OAuth 2.0 Token Introspection (RFC 7662) request.

// POST https://<tenant>/oauth2/introspect
form.Set("client_id",       "9ada0c66-...")
form.Set("client_secret",   "TvFt1rBA9...")
form.Set("token",           "<access_token>")
form.Set("token_type_hint", "access_token") // optional hint, speeds up lookup

Response struct

type IntrospectionResponse struct {
    Active            bool   // is the token currently valid?
    ClientID          string // which client issued the token
    Username          string // Cloud Directory username e.g. "Bretton"
    PreferredUsername string // OIDC preferred_username claim
    Name              string // full display name e.g. "Jessica"
    GivenName         string // first name
    Subject           string // IBM Verify internal user ID e.g. "6430083CO1"
    Scope             string // granted scopes
    TokenType         string // "bearer"
    Issuer            string // token issuer
    IssuedAt          int64  // Unix timestamp
    ExpiresAt         int64  // Unix timestamp
}

If IBM Verify doesn't include a field (like username), Go's json.Unmarshal leaves it as the zero value ("" for strings) — no error, just empty.

11. internal/datasources/token_introspection_data_source.go — data.verify_token_introspection

internal/datasources/token_introspection_data_source.goGo — Terraform data source

The Terraform wrapper around IntrospectToken(). Implements datasource.DataSource — a different interface from resource.Resource.

Data source vs resource — why it matters here

ResourceData Source
Interfaceresource.Resourcedatasource.DataSource
MethodsCreate, Read, Update, DeleteRead only
When Read runsOnly when Terraform thinks state is staleEvery single plan and apply
StatePersisted across runsRecomputed every run
Why introspection must be a data source: A token expires in 60 minutes. If it were a resource, Terraform would call Create once, store active=true, and show that for hours. As a data source, Read() is called on every apply — the result always reflects right now.

Read method

func (d *TokenIntrospectionDataSource) Read(ctx, req, resp) {
    var config TokenIntrospectionDataSourceModel
    req.Config.Get(ctx, &config)        // 1. read inputs from HCL config

    result, _ := client.IntrospectToken(ctx, ...)  // 2. call IBM Verify

    config.Active    = types.BoolValue(result.Active)   // 3. map response
    config.Subject   = types.StringValue(result.Subject)
    // ... all fields

    resp.State.Set(ctx, &config)        // 4. store result in data source state
}

Note: data sources use req.Config (not req.Plan) to read inputs — because data sources have no plan, only current config.

12. examples/cert/main.tf — One-Time Certificate Root

examples/cert/main.tfHCL — Terraform config

A completely separate Terraform root with its own terraform.tfstate. Run once, never touched again.

resource "verify_certificate" "this" {
  common_name   = "DemoTokenSigner"
  validity_days = 365
  key_size      = 4096
  ...
}
# Writes cert.pem to examples/ for uploading to IBM Verify
resource "local_file" "certificate" {
  content  = verify_certificate.this.certificate_pem
  filename = "${path.module}/../cert.pem"
}
# Writes key.pem to examples/ for use by verify_jwt
resource "local_sensitive_file" "private_key" {
  content  = verify_certificate.this.private_key_pem
  filename = "${path.module}/../key.pem"
}
Why a separate root? Terraform state is per-root. By putting the cert here, a terraform destroy in examples/ never touches this root — the key pair survives and IBM Verify's trust relationship remains intact.

13. examples/main.tf — Main Terraform Config

examples/main.tfHCL — Terraform config

The main config run on every terraform apply. Five logical sections:

Section 1 — Read stable private key from disk

locals {
  private_key_pem = file("${path.module}/key.pem")
  # Reads the key written by examples/cert/ — same key every time
}

Section 2 — Sign a fresh JWT

resource "random_uuid" "jwt_id" {}  # new UUID each destroy/apply cycle

resource "verify_jwt" "custom" {
  issuer             = "https://demo.ibm.com"
  subject            = "bretton"         # username in IBM Verify
  key_id             = "demotokensigner" # cert label in IBM Verify
  jwt_id             = random_uuid.jwt_id.result
  private_key_pem    = local.private_key_pem
  expires_in_seconds = 900               # 15 minutes
}

Section 3 — Exchange JWT for access token

resource "verify_token_exchange" "example" {
  tenant_url         = var.verify_tenant_url
  client_id          = var.sts_client_id
  client_secret      = var.sts_client_secret
  subject_token      = verify_jwt.custom.token    # output of the JWT resource
  subject_token_type = "urn:demo:token-type:user-jwt"
}

Section 4 — Introspect the access token

data "verify_token_introspection" "example" {
  tenant_url    = var.verify_tenant_url
  client_id     = var.sts_client_id
  client_secret = var.sts_client_secret
  token         = verify_token_exchange.example.access_token  # chained from above
}

Section 5 — Outputs

All output blocks expose values after apply. Sensitive ones (access_token, jwt) are hidden by default — use terraform output -raw access_token to reveal.

Dependency chain: Terraform automatically infers the creation order from references. verify_jwt waits for random_uuid, verify_token_exchange waits for verify_jwt, and data.verify_token_introspection waits for verify_token_exchange. You never declare this order explicitly.

14. Key Concepts Explained

go.mod — dependency management

Declares two direct dependencies:

  • github.com/golang-jwt/jwt/v5 — JWT creation and signing
  • github.com/hashicorp/terraform-plugin-framework — the Terraform provider SDK

Everything else (gRPC, protobuf, logging) is an indirect dependency pulled in automatically.

types.String vs string

All model struct fields use types.String, not plain string. This is because Terraform values have three states: known, null, and unknown. Plain string can't represent null or unknown. The framework types handle all three.

Sensitive: true

Any attribute with Sensitive: true in the schema is redacted in Terraform plan/apply output and in the state file. The value is still stored — it just won't be printed. This is used for private_key_pem, client_secret, access_token, and token.

var _ resource.Resource = &CertificateResource{}

This line appears at the top of every resource file. It's a compile-time check — if CertificateResource doesn't implement all methods of the resource.Resource interface, the build fails immediately. It produces no runtime code.

go build -o terraform-provider-verify .

Must be run from the project root after every Go code change. Produces the binary that Terraform loads via the dev_override in ~/.terraformrc. Without this step, Terraform runs the old binary and ignores your changes.
